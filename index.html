Over-the-Air Updates for React Native

OpenOTA is a project I created and maintain in the open — an over-the-air (OTA) update system for React Native apps. It lets teams ship JavaScript-bundle updates directly to users, without waiting on app-store review for every change, while keeping releases organized, reversible, and safe.

License MIT Stack React Native · Node.js Status Active · Open Source

OTA workflow

1 Build JS bundle
→
2 Publish to a release channel
→
3 App checks & downloads update
→
4 Apply on next launch
→
5 Roll back instantly if needed
React Native integration
A lightweight client SDK checks for and applies bundle updates with minimal app-side integration effort.
Release channels
Ship to staging, beta, or production channels independently — test an update before it reaches every user.
Rollback
A bad release can be reverted immediately without publishing a new app-store build.
Developer workflow
Deployment is designed to slot into an existing CI/CD pipeline rather than replace it.

Case Study · Production Application

NearDeals

↗ Full Case Study Page ▶ Play Store ✉ Ask About It

Overview

NearDeals is a local commerce discovery platform — an Android app backed by a Node.js/Express API — that connects nearby buyers with real shops and dealers. It covers both single dealers (independent shops) and chain dealers (multi-branch retailers), each with their own product catalog and store profile.

Problem

Local buyers often can't tell which nearby store actually stocks a product, at what price, or how far away it is — search is fragmented across calls, walk-ins, and outdated listings. Store owners, meanwhile, have no lightweight way to publish their catalog and be discovered by distance.

Solution

A catalog and discovery layer built around location: users search or browse by category, see results ranked by distance and store reliability, and open a product/store detail view with specs, pricing, offers, and direct contact (call, WhatsApp, directions) — the flow shown alongside.

My Contribution

Engineering the Android application UI and the backend API layer — including the product/catalog domain (models, services, controllers, validation), dealer and store management, category structure, and the location/distance-based discovery logic.

Architecture & Engineering Highlights

Dealer model
Distinct data model for single dealers vs. chain dealers, so a chain's branches share a catalog while remaining independently discoverable stores.
Catalog service layer
Product domain split into model / service / controller / validation layers with normalized naming and indexed lookups for fast search.
Location-based discovery
Store and product results ranked by proximity, so "what's near me" resolves quickly against a growing store network.
Authentication
Token-based auth separating buyer and dealer roles, gating store/catalog management behind verified dealer accounts.

Key Challenges

Modeling a catalog that works identically for a single independent shop and a multi-branch chain, without duplicating product data per branch. Keeping search and distance-ranking responsive as the store and product count grows required indexed queries over ad-hoc scans.

Performance & Scalability

Search, filtering, and product-detail screens are built to stay responsive as catalog size grows — indexed MongoDB queries on the fields users actually filter by, and a mobile UI designed to load progressively rather than block on a full catalog fetch.
