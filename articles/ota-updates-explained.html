How Over-the-Air Updates Work in React Native

By Ravuri Harsha · Creator & Maintainer of OpenOTA

Every React Native app is really two things bundled together: native code (compiled per-platform, distributed through the App Store / Play Store) and a JavaScript bundle (the app's UI and logic, which the native shell downloads and runs). Over-the-air (OTA) updates exploit that split — if a change is pure JavaScript, it can be delivered directly to installed apps without going through app-store review at all.

What actually happens on an OTA update

  1. Build. A new JS bundle is produced from the app's source — the same bundle that would normally ship inside a native build.
  2. Publish to a channel. The bundle is uploaded to a specific release channel (e.g. staging, beta, production), not broadcast to every install at once.
  3. Client check. The app checks in — usually on launch or resume — asking whether a newer bundle exists for its channel.
  4. Download. If there's a newer version, it's downloaded in the background.
  5. Apply. The new bundle is swapped in, typically on the next app launch, so the update doesn't interrupt an active session.
  6. Rollback path. If the new bundle causes crashes or regressions, the channel can be reverted to the previous bundle, and clients pick that up the same way they picked up the update.

What OTA can and can't ship

This is the part teams get wrong most often. OTA only covers what lives in the JS bundle.

Can ship OTACannot ship OTA
UI changes, screen logic, copyNew native modules or SDK upgrades
Bug fixes in JS/business logicChanges to native permissions (camera, location)
API endpoint or config changesApp icon, name, or native entitlements
Most React Native library updates (JS-only)Anything requiring a new native build (Xcode/Gradle)

If a change touches native code, it has to go through the normal app-store release — OTA is a fast lane for the JS-only subset, not a replacement for native releases.

Why channels matter

Pushing every update straight to 100% of production users is how a bad release becomes a bad incident. Channels let a team publish to staging or beta first, validate on real devices, then promote the same bundle to production — rather than re-testing a totally separate build. This is also where rollback becomes cheap: reverting a channel is just re-pointing it at the previous known-good bundle.

Where OpenOTA fits

OpenOTA is my open-source implementation of this workflow for React Native — a release-channel and update-delivery system with a lightweight client SDK, built so a bad release can be reverted without waiting on a new app-store build.
